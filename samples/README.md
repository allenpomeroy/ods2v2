# samples/

## `empty_ods2_volume.dsk.gz` — a ready-to-use starter volume

A genuine, empty ODS-2 volume, created by my VAX/VMS vax8600 OpenVMS 7.1
`INITIALIZE` command. RA92 disk geometry, 2,940,951 blocks. Not
generated by this project's code.

Get a working volume with:

```bash
make starter-volume
```

This decompresses the pristine empty RA92 disk to `./transfer.dsk`,
which is the filename every example and tool in this project assumes.
Existing transfer.dsk will not be overwritten, so it's safe to run even if
you've already got one with real data on it.

```bash
make starter-volume
./ods2 transfer.dsk DIR
./ods2 transfer.dsk CREATE/DIRECTORY [MYSTUFF]
```

### Why did you not create an INITIALIZE command?

Short answer:
Safer, lower-risk choice as creation of all the system indices, home block,
map files is very complicated. I've left that for some other enterprising
individuals. Besides, you need to have a VMS system running to get value
from this project anyway. Just saying.

The pre-made volume, is something I've already run `ANALYZE/DISK` against
dozens of times over the course of this entire project, through every
round of write-path development - and it has never once come back with a
complaint (unless I introduced a bug).

If you need a volume at a different size or geometry than this one, use a
real `INITIALIZE` via SIMH remains the correct tool for that job.

### Verifying it yourself

```bash
make starter-volume
gunzip -c samples/empty_ods2_volume.dsk.gz | cmp - transfer.dsk && echo "matches"
file transfer.dsk
```

`file` should report:
```
transfer.dsk: Files-11 On-Disk Structure (ODS-2); VAX/VMS
or OpenVMS file system; volume label is 'TRANSFER    '
```

## Other files in this directory

Everything else here is just for historical completeness - used 
during development.

`sample.bin` > `indexf_headers.bin` > `root_dir.bin`
- are small, real, VMS-written fragments extracted during
this project's development, used by the automated test suite
(`make test`) to validate reading/writing logic against genuine
on-disk bytes.

`synthetic_disk.img` > `synthetic_disk_working.img`
- are generated by `tools/build_synthetic_disk.py` at test time
(not stored in the repository) by assembling those
fragments into a full, sparse test image.
